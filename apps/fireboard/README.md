# FireBoard temperature dashboard

Stdlib-only Python 3.10+ BusyBar app. No packages, credentials or hardware needed
for demo/recording. Direct HTTP BusyBar output, 72×16 LEDs; no deployment required.

```sh
/usr/bin/python3 apps/fireboard/app.py --demo --host 127.0.0.1:8080
/usr/bin/python3 apps/fireboard/app.py --source apps/fireboard/sample.json --config apps/fireboard/config.json --host 127.0.0.1:8080
```

Without `--source`, demo data is used (synthetic temperatures, not live readings).
Without `--host`, output goes to the standard USB address `10.0.4.20`.
Only run against your bar when you intend to display there. Ctrl-C/SIGTERM releases
the application's elements. A 409 (another application owns the screen) is harmless.
`--test` draws once and exits. `--interval 3` sets page duration and input poll period.

## Supported ingestion

**Implemented:** normalized JSON file or HTTP(S) bridge URL via `--source`.
**Not implemented:** direct official FireBoard cloud API, login, alert discovery,
Bluetooth, or device access. This app does not assume any undocumented FireBoard
endpoint or alert schema. Live FireBoard integration is unverified. A bridge must
translate its supported upstream format to the contract below. See the independent
repository ingestion research in `docs/fireboard-ingestion.md` when available.

```json
{"unit":"F","updated_at":1700000000,"channels":[
  {"id":"1","temperature":158,"connected":true},
  {"id":"2","temperature":null}
]}
```

`updated_at` is a Unix timestamp in **seconds**, not file retrieval time. Refresh it
only when new measurements arrive. Each channel may override `unit` and
`updated_at`. IDs must be unique; temperatures must be finite JSON numbers or
null. Missing configured channels, null temperatures, or `connected:false` mean
disconnected. Missing timestamps, timestamps over 30 seconds in the future, or
age greater than `stale_after` (default 120 seconds) mean stale. The checked-in
sample intentionally has an old timestamp and demonstrates stale warnings.
File writers should use atomic rename to avoid partial JSON reads.

A bridge URL may authenticate using `FIREBOARD_BRIDGE_TOKEN` (Bearer header),
loaded from the environment only. Set it through your local secret manager or
shell environment; never put tokens in the source, config, URL, screenshots or
Git. Authenticated bridges require HTTPS. Redirects are rejected to prevent token
leakage. Requests time out after 10 seconds, URL responses are limited to 1 MiB;
failed input displays SOURCE ERROR instead of silently reusing cached readings.
Errors intentionally do not log URLs, payloads or credentials. The config is read
once at startup; input is fetched every page. No automatic retries/backoff beyond
the normal page loop. Choose an interval compatible with your bridge rate limits.

## Configuration and display

Copy `config.json`. `unit` is display/config unit (`F` or `C`); incoming readings
are converted, but configured `targets` and `baseline` are already in this unit.
If you switch config unit, also convert its targets and baseline.
`channels` maps source IDs to `label` (ASCII alphanumeric/spaces, displayed first
four characters), `role` (`food`, `pit`, `grate`, `ignore`), optional `targets`,
and optional `baseline` (default 32 F / 0 C). Use distinct short labels.
Targets must exceed baseline. They are sorted and deduplicated.

Overview pages show two readings each, with role F/P/G, OFF or OLD. Detail pages
show each channel's reading, **NEXT** target and a graphical progress bar. Pages
rotate through all overviews then all probes, including pit/grate. Small type is
intentional for the physical 72×16 constraint. Progress is from the last reached
milestone (or baseline) to the next strictly higher target. At exact equality,
the next milestone becomes active; after the last target, DONE and a full bar
appear. No configured target shows NO TARGET. Stale/disconnected values have no
progress. OLD/STALE takes precedence over disconnected if both apply.

These are **user-configured heating milestones**, not downloaded FireBoard
alerts. No targets are inferred from temperature; demo targets are examples only.
Cooling thresholds, alert notifications, latched crossings, pit low/high alarms,
and food-safety advice are not supported. Temperature falling below a prior
milestone selects it again. This is a visual monitor, not a safety alarm.

## Verification

```sh
/usr/bin/python3 -m unittest discover -s apps/fireboard -v
PATH=/usr/bin:/bin:$PATH npm run preview -- fireboard --png -- --demo
PATH=/usr/bin:/bin:$PATH npm run check -- fireboard --run
npm run build
```

Preview is generated by the repository recorder/emulator renderer, not a mockup.
HTTP tests use mocks; private credentials and physical hardware are not tested.
