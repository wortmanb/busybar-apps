# FireBoard ingestion and BusyBar display (72×16)

**Recommendation:** Ship a read-only host process with demo/JSON input and an optional FireBoard Cloud adapter. Use one shared `/api/v1/devices.json` poll every 30 seconds as the first live integration; it can supply temperatures and alert metadata in the same response. Configure probe roles and optional explicit thresholds. Keep the official FireBoard app as the alerting authority. Add HA/bridge ingestion next only if there is an existing deployment or a need for offline operation.

**Evidence boundary (public sources reviewed 2026-11-25):** FireBoard documentation verifies supported endpoints and product behavior. Community code/fixtures below corroborate potential wire fields and local integrations, not vendor guarantees. No login, account inspection, physical testing, firmware testing, or live payload capture was performed. Lack of public documentation is not proof that a feature cannot exist.

## Official cloud: implementation contract

[FireBoard Cloud API v1](https://docs.fireboard.io/app/app-api/) is the primary source. Use HTTPS to `fireboard.io` and send an identifying `User-Agent` on **every** request, including login. Exchange FireBoard username/email and password via `POST /api/rest-auth/login/` with JSON `username` and `password`; response is `{"key":"…"}`. Subsequent requests use `Authorization: Token <key>` (not Bearer). Prefer an already provisioned token, or exchange the password once on the host; do not repeatedly log in or store the password if the token suffices. Public docs do not specify OAuth/scoped read-only tokens, expiry/refresh semantics, or a subaccount model. Treat this as an account secret even though this adapter only performs reads.

| GET path (prefix `/api/v1`) | Use and caveats |
| --- | --- |
| `/devices.json` | List account devices; use the documented `latest_temps` (samples older than 60s omitted), `channels` (labels, alerts and notification settings), and device `last_templog` metadata. Filter to configured devices in one response. |
| `/devices/<UUID>.json` | Single-device detail; potential alternative to the list poll for a single device, not an extra high-frequency call. Key by returned UUID, not serial number or title. |
| `/devices/<UUID>/temps.json` | Current readings only; omits channels without a sample younger than one minute. Useful for troubleshooting or an alternative with separately cached metadata, not in addition to each list poll. |
| `/devices/<UUID>/drivelog.json` | Recent Drive telemetry only (<1 minute). A Drive setpoint, fan %, or internal board temperature is not measured pit or grate temperature. Not needed in v1. |
| `/sessions.json`, `/sessions/<id>.json` | Browse current/historical cook metadata, not the hot path. [Sessions docs](https://docs.fireboard.io/app/app-sessions/) say sessions auto-start, close after 30 minutes of inactivity and roll over at 24 hours; start/end can be edited. Session presence is not proof of freshness. |
| `/sessions/<id>/chart.json` | Historical series per device/channel; arrays `x` (Unix timestamps), `y` (temperature or Drive %), plus `degreetype` (1=C, 2=F), `device` and `label`; `?drive=1` adds Drive data. Avoid polling the full chart; useful for investigation or offline demos. |

### Wire compatibility notes for `apps/fireboard`

- **Stable role mapping:** configure `{device UUID, channel number}` for each named food probe, `PIT`, and `GRT`; labels are display hints only. Pit and grate need two actual sources if both are to be displayed. Do not duplicate one probe or infer roles from `Ambient`, array order or port count. The community [FBX2D fixture](https://github.com/gordlea/fireboard2mqtt/blob/HEAD/tests/fixtures/devices_fbx2d.json) has lowercase `uuid`, `channels[].channel`, `channel_label`, duplicate names, and historical/placeholder channels with `state: null`; `state: true` can coexist with empty `latest_temps`. Do not use the metadata `id` as a port number or treat `enabled`/`state` as a freshness signal.
- **Reading shape:** [ha-firebuilt's reader](https://github.com/awcab/ha-firebuilt/blob/HEAD/custom_components/fireboard/sensor.py) reads `latest_temps[].channel`, `temp`, `degreetype` and `created`, with device-level unit as fallback. [`mirkop/fireboard_integration`](https://github.com/mirkop/fireboard_integration/blob/HEAD/custom_components/fireboard/api.py) handles `/temps.json` as an array of `{channel,temp,...}`. These are compatibility leads, not complete schemas from FireBoard. Prefer per-reading timestamp and unit; if timestamp is absent from a valid live-only result, keep observation time separate and do not assume the sample was taken at poll time. Device-level `last_templog` cannot establish per-probe freshness. Do not substitute a previous cook's chart or an undated `channels[].last_templog`/`current_temp` as fresh data.
- **Normalize once:** use one internal snapshot per source (channel key, role, label, value, unit, sample time if known, observation time, threshold(s), availability). Normalize temperatures and thresholds into the same unit; °C/°F differences scale by 9/5, **without** a 32° offset. Treat absent/invalid/unknown-unit data as unavailable instead of guessing °F or coercing blanks to zero. Preserve legitimate zero values. Skip malformed items without discarding unrelated valid probes.
- **Alert shape:** the vendor documents alert values on `channels`, but no standalone alert, delivery-state, or ETA endpoint in the public API reference. The FBX2D fixture shows `channels[].alerts[]` with `enabled`, nullable `temp_min`/`temp_max`, `session_id`, `time_start`/`time_stop`, `minutes_buffer`, `minutes_repeat`, and notification flags. Treat these fields as observed, not universal. Join alerts to the current selected channel; do not reuse a historical or ambiguous session's alert. Only use live cloud thresholds when applicability, enablement, and units are understood; otherwise prefer explicitly configured local targets clearly identified as such. Don't require a sessions poll for basic temperature rendering.

### Distance to next alert

Show **degrees to the nearest eligible threshold**, not time to a notification. For an upper limit the gap is `threshold – reading` (up arrow); for a lower limit it is `reading – threshold` (down arrow). Minimum/maximum are inclusive, so use `HIT` at a crossing (or exactly equal) and otherwise choose the smallest positive gap, with stable tie-breaking. If multiple boundaries are breached, `HIT` wins over a still-distant limit. No current reading or no usable threshold → `--`; never calculate a new gap from a stale value. Keep one probe per page so its gap cannot be mistaken for another's. If rounding would turn a positive gap into zero, show `<1` rather than `HIT`.

[Official alert rules](https://docs.fireboard.io/app/app-alerts/) permit multiple alerts, min/max, timing windows, buffers and repeat intervals. Displaying a crossed threshold does not mean a notification has fired or is due, and unsupported schedules cannot be silently treated as all-day. FireBoard's [Analyze](https://docs.fireboard.io/app/app-analyze/) has an in-app prediction tool, not a documented cloud API ETA; do not extrapolate through cooking stalls in v1. No alert writes, notification delivery claims, or Drive controls.

### Cadence, failure handling and privacy

- The vendor currently specifies **17 requests per rolling five minutes per originating IP**, not the older community shorthand of 200/hour. One call/30s is about 10/5 min, leaving room for login and occasional discovery; two calls/30s is about 20/5 min and exceeds the limit. One call/20s is already ~15/5 min. Budget across devices, workers, retries and other tools on the same NAT; use one poller/cache for all bars. Render/rotate independently of the network cadence.
- Set finite timeouts. On throttling, honor `Retry-After` if present and otherwise stop requests for at least five minutes before a paced retry; do not keep probing a rate-limited IP. Back off transport/5xx failures; stop repeated requests on credential rejection until configuration is fixed. Cloud latency includes device upload/relay, FireBoard processing, and the next poll; 30 seconds is a poll period, not a maximum age or service SLA. No internet/cloud/device uplink → no new cloud readings.
- Successful snapshot with an omitted probe is not a fresh measurement and may mean unplugged, aged out or disconnected. Show `--` (or a briefly retained value explicitly marked stale); on poll failure, mark cached data stale immediately and blank it after a bounded expiry. Never reset freshness on render, cache hits, HTTP errors or unchanged sample timestamps. Display missing per channel so another probe can remain live; distinguish whole-source states such as `OFFLINE`/`AUTH` from no probe.
- Keep account token on the ingest host in environment/secret storage; no secrets, raw account payloads, cookies, public share links or identifying metadata in Git/logs/screenshots or on the bar. Forward only the readings/display fields needed. A public cloud link or browser bundle is not a secret store.

## 72×16 display proposal

Use two 36-pixel columns and two fixed rows. Rotate **food probe only**, roughly every 4 seconds; keep `PIT`/`GRT` stationary on every page. At a threshold crossing, prioritize that food page on the next rotation without hiding other probes indefinitely. One frame (visual grouping, not a literal bitmap):

```text
        x=0–35              x=36–71
      ┌──────────────────┬──────────────────┐
 top  │ B1   157°F        │ ↑  8°            │
      ├──────────────────┼──────────────────┤
 base │ PIT  247          │ GRT 232          │
      └──────────────────┴──────────────────┘
```

Render one-pixel margins and gutter. Use a 3×5 bitmap font with one-pixel spacing (up to eight glyph cells in each 34-pixel usable width); `B1 157°F` fits in 31 pixels. Align a 5×7 food number if space permits: three 5×7 digits with 1px gaps occupy 17 pixels, leaving room for the two-glyph alias and unit. Example rows: y=0–6 and y=9–15, with one or two unlit separator rows. Keep food aliases to two glyphs; add an explicit °C/°F cue on each normal frame, shared by both ambient values. For sign/three-digit extremes, fall back to the small font and test overflow rather than clipping. Use white for food, amber for gap, and muted cool colors for ambient; retain labels, arrows, `HIT`, `--`, and a `~` stale marker (or blank-on-stale), so color is not the only cue. No marquee or decorative chart; the stable ambient row is more useful at a glance. Preview/demo should cover both units, unplugged food or ambient probe, no threshold, lower/upper crossing, and offline/auth errors.

**Handoff and acceptance:** Develop against synthetic JSON for multiple devices, duplicate labels, empty `latest_temps`, old/missing timestamps, unit conversion, nullable thresholds and mock throttling/auth/network errors. Later, an authorized operator can confirm the exact model/firmware, payload fields and units with an actual cook: change an alert, unplug one probe, verify roles and stale states, and test disconnect/reconnect and rate budgeting. For an offline bridge, additionally demonstrate data with WAN unavailable and check official-app coexistence. None of those physical checks is implied by this report.
